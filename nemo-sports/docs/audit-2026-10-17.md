# NEMO Sports audit — 2026-10-17

**Target:** `https://nemo-sports.vercel.app/`  
**Repository baseline:** `f95c0484890eaf87e57b90b130386231a24e7a8c`

**Deployment/data/auth:** No production deployment, database or user-data changes, credential/permission changes, or authentication changes were made.

## Executive summary

A live English internal-link failure is confirmed: the English Egyptian Premier League table links team rows to `/en/teams/<provider-slug>`, but three sampled destinations (Pyramids FC, Al Ahly FC and Zamalek SC) rendered NEMO's “Page not found” page. Their Arabic counterparts rendered team pages. The public standings API separately returned a fresh 20-row Egyptian table, including Pyramids' `teamProviderId: "Pyramids FC"` and `teamProviderSlug: "pyramids-fc"`.

The slug itself is supported by the repository's link builder and resolver; this is not simply a “slug versus provider ID” mismatch. The team detail page falls back from the provider's unsupported direct team endpoint to standings lookup. That lookup discarded table-fetch failures and could turn an inconclusive provider outage into `notFound()` (and an ISR-cached 404). A focused change now preserves that distinction: a matching row resolves as before, transient standings failures no longer prove the team is absent, and a confirmed unknown slug still returns not-found when no transient lookup failure occurred. This is a source-level repair; production was not deployed or rechecked with the modified code.

Other high-priority issues remain deliberately unchanged: the anonymous `GET /api/cron/update-matches` can trigger the matches job, and the English Egyptian competition page renders an Arabic breadcrumb/H1. Fixing cron access would alter authentication/permissions and needs explicit approval.

## Findings

### P2 — English competition table links render team 404 pages

**Evidence:** The production page `/en/competitions/egyptian-league` rendered a 20-team table with a link to `https://nemo-sports.vercel.app/en/teams/pyramids-fc`. Direct fetches of that link and the Al Ahly/Zamalek links rendered the site's 404 page. The corresponding Arabic routes `/teams/pyramids-fc`, `/teams/al-ahly-fc` and `/teams/zamalek-sc` rendered team content. The production standings endpoint `/api/v1/football-data/standings?competition=egyptian-premier-league` returned 20 rows from SportScore with `fromCache:false`, `stale:false`, and Pyramids' provider ID and slug at `2026-10-17T02:30:09.625Z`.

The fetch tool exposes rendered content but not the HTTP status header; therefore this report verifies the rendered 404 page, not the numeric production status code. Direct production `curl` requests were blocked by TLS error 35.

**Cause:** `teamHref()` prefers the provider slug, and `findTeamRow()` matches provider slug, ID, and display-name aliases. The Egyptian competition is included in the covered-team lookup. SportScore does not provide the direct team-detail capability, so the page relies on its standings fallback. Before this change, failed standings requests were silently skipped; a no-match result then fell through to `notFound()`. The exact failing provider response/cache event on Vercel is unavailable, so the production request's precise trigger is not proven.

**Repair:** Added a tri-state standings resolver in `lib/team-lookup.ts` and used it from `views/team-detail.tsx`. A confirmed row still wins; a transient failed table lookup with provider attempts now throws rather than caching a false 404; a missing provider configuration with no attempts and a clean no-match remain eligible for an honest 404. URLs, team IDs, data sources, and page design are unchanged.

**Regression coverage:** Added tests for provider-slug round trips, transient table failure, no-provider configuration, a found row despite an unrelated failure, and unknown-team behavior. `npm run links:test` passes (24 tests total).

**Remaining:** The changed code is local only. Recheck these exact production links after an approved deployment; an existing ISR-cached 404 may persist until revalidation or cache invalidation.

### P1 — Anonymous match-update cron trigger

**Evidence:** Source and cron regression tests show that `GET /api/cron/update-matches` can trigger `runJob` without authentication. Local smoke also observed the route's current behavior; the endpoint was not invoked on production.

**Risk:** Public requests may cause provider calls and match-data writes/resource consumption. Production impact and quota consumption were not measured.

**Action:** Left unchanged per scope constraints. Authentication/permission changes require explicit approval; do not test this endpoint against production.

### P2 — English Egyptian competition page contains Arabic heading/breadcrumb

**Evidence:** The local production build rendered `/en/competitions/egyptian-league` with English title, description, canonical and hreflang metadata, but an Arabic breadcrumb and H1. `views/competition-detail.tsx` unconditionally renders `competition.nameAr` in that provider competition view.

**Action:** Not changed in this link-focused repair. A locale-aware display-name selection can be a small follow-up with a regression test. Production has not been independently verified for this heading defect.

### P2 — Production match-count discrepancy (unresolved)

**Evidence:** Production fetches showed 54 editorial-labeled fixtures on `/en`, while `/`, `/matches?date=today&sport=football`, and its English equivalent showed 253. The public match API reported fresh, non-cached, non-degraded, non-stale data at `2026-10-17T02:17:54.989Z`. The local `db/admin-matches.json` contains 125 records, 54 dated 2026-10-17; this is a lead, not proof of the production cause.

**Action:** No data or gateway changes made. Production provider/cache/admin telemetry and a consistent same-time response comparison are needed before attributing the mismatch.

### Source-level bilingual metadata concerns — not runtime-confirmed

Code review found English metadata paths that select Arabic-only admin names for teams, players and competitions; manual-news metadata uses `title` rather than `titleEn` and hardcodes `openGraph.locale` as `ar_AR`; provider team detail uses an Arabic competition label. Published admin records were not available for runtime reproduction. These remain unmodified pending focused tests against representative published records. Editorial-news JSON-LD also needs a locale-specific URL/text review; English article content lacks separate English body/description fields, so no speculative translation was added.
